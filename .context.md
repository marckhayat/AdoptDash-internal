## What this dataset is

This data comes from a **Workspan export** used by the Cisco CX Partner Organization. It tracks **CPI Adopt rebate** performance across Cisco partners. Each row represents one **deal × use-case** combination (a partner's deal for a specific product use case).

There are two report variants:
- **Report 19849** — Partner-level data (one row per partner deal × use case)
- **Report 21766** — Distributor-level data (same structure, adds `Disti Name` and `2T Partner Name` columns)

## Key concepts

| Term | Meaning |
|---|---|
| **CPI Adopt** | Cisco Partner Incentive — Adopt rebate program. Partners earn rebates for driving customer adoption through defined lifecycle stages. |
| **Use Case** | A specific adoption scenario (e.g. "Campus Network Automation"). Each use case belongs to one Offer and one Portfolio. |
| **Offer** | Product family (e.g. "Catalyst Center", "Meraki", "Cisco Umbrella"). |
| **Portfolio** | Top-level grouping: `Networking`, `Security`, `Cloud + AI Infrastructure`, `Collaboration`. |
| **Stage** | Eligibility status of the deal: `Eligible`, `Expired`, `Not Eligible`. |
| **Lifecycle stages** | Ordered progression: Purchase → Onboard → Implement → Use → Engage → Adopt → Completed. |
| **Opt-In** | Partner must opt in to receive rebates. `Adopt Rebate Opt-In Status` = `Opted In` / `Pending` / `Not Opted In`. |
| **PVI** | Partner Value Index — an engagement score (0–10) measuring adoption breadth and depth across portfolios, based on the last 18 fiscal months. |
| **BE GEO ID** | Unique identifier for a partner's geographic business entity. |
| **CR Party ID / CR Party Name** | Partner identifier and name. |
| **EA Flag** | Enterprise Agreement flag (`Yes`/`No`). |
| **AAP Flag** | Adoption Accountability Planning flag (`Yes`/`No`). |
| **Maximum Incentive Deal Flag** | `Yes` if the deal qualifies for maximum incentive tier — used for PVI eligibility. |

## Data normalization rules

Raw Workspan exports contain known data quality issues. Before analyzing, apply these fixes:

### 1. Offer (Track) rename
If `Track` = `"Integrated Secure Operations"`, treat it as `"Cisco Secure Network Analytics"`.

### 2. Use case (Sub-Track) rename
If `Sub-Track` = `"Cisco Secure Network Analytics"`, treat it as `"Network Security Analytics"`.

### 3. Missing or invalid Portfolio
If `Deal CPI Portfolio` is blank or `"No Offer"`, look up the correct portfolio using the hierarchy table above:
- First try matching `Track` to the **Offer** column in the table → use that row's Portfolio
- If no match, try matching `Sub-Track` to the **Use Case** column → use that row's Portfolio
- If still no match, leave as-is

### 4. Opt-in eligibility constraint (one use case per offer per customer)
When a partner opts in for more than one use case within the same **offer (Track)** for the same **CR Party ID** (customer), only **one deal remains Eligible** — the rest flip to **Not Eligible**. This is enforced by Workspan after opt-in.

Consequence for analysis:
**Consequence for analysis:**
- When identifying opt-in opportunities for non-opted-in eligible deals, show **all available UC options** grouped by `(CR Party Name, Track/Offer)` — one row per use case. The user will decide which one to opt into per group.
- Do **not** pre-select the best deal per group — that decision belongs to the user.
- When computing a **realistic maximum potential** (if the partner were to opt in optimally), then apply the constraint and sum only the highest-potential UC per `(BE GEO ID, CR Party ID, Track)` group.
- Summing potential incentives across all non-opted-in eligible deals without this deduplication will **overcount** both deal count and dollar potential.

### 5. Locked deals
A deal is **locked** when it is **opted-in AND has already earned incentives** (`Estimated Earned Incentives > 0`). A locked deal permanently consumes the opt-in slot for that `CR Party ID + offer` combination — no other use case under the same offer for that customer can ever be opted into.

- To find locked deals: filter `Adopt Rebate Opt-In Status = "Opted In"` AND compute earned incentives using the 3-condition check (see Analytical checklist §3) — keep only rows where earned > 0.
- Locked deals may still be **Eligible** (still progressing, still earning) or **Expired** (fully consumed — the incentive window has closed).
- Eligible locked deals with stages still in progress (e.g. current stage = Engage or Adopt) are worth monitoring — completing those stages earns additional incentives.

### 6. Use the hierarchy table as ground truth
If any row has a `Track` / `Sub-Track` combination that looks mis-categorized, always resolve Portfolio, Offer, and Use Case by cross-referencing the **Incentive type per use case** table. That table is the authoritative source.

## Analytical checklist — always verify before returning numbers

Before returning any counts or amounts, confirm these conditions are applied:

### 1. Actionable deals must not be expired
When counting deals that a partner can still act on (opt-in opportunities, deals in progress, incentives at stake), always filter:
- `Deal Incentive Expiry Date >= today`

Expired deals cannot earn incentives and must not be counted as actionable, even if their `Stage = "Eligible"`.

### 2. Opt-in opportunity filters
A deal is a genuine opt-in opportunity only if ALL of the following are true:
- `Stage = "Eligible"`
- `Adopt Rebate Opt-In Status ≠ "Opted In"` (the deal itself is not opted in)
- The offer is not already opted in for that partner × customer: no other row with the same `BE GEO ID + CR Party ID + Track` has `Adopt Rebate Opt-In Status = "Opted In"`
- `Deal Incentive Expiry Date >= today`

### 3. Earned incentive conditions — check all three per stage
For each of the 4 stages (Onboard, Use, Engage, Adopt), a stage amount counts toward earned incentives **only if all three conditions are true**:
1. `Stage Completion Flag = "Yes"` — the stage was completed
2. `Stage Completion Date >= Adopt Rebate Start Date` — completed after the LCI rebate window opened (pre-LCI completions do not count even if the flag is set)
3. `Stage Completion Date <= Deal Incentive Expiry Date` — completed before the deal expired

Evaluate these independently for each stage. A deal can have partial earned amounts — e.g. Onboard earned but Engage not, because Engage completed after expiry. Skipping any condition on any stage leads to overcounting.

## Common analysis patterns

When the user pastes data and asks questions, here are the formulas to apply:

> **Important:** The CPI Adopt tab's "By Use Case" charts (opt-ins and earned) only include rows where `Maximum Incentive Deal Flag = "Yes"`. Apply this filter when replicating those charts.

**Opt-in rate** = count of rows where `Adopt Rebate Opt-In Status = "Opted In"` ÷ total rows (Eligible stage only)

**Earned incentives** = sum of `Estimated Earned Incentives` (deduplicate by `Deal WS-ID` if needed)

**Missed incentives** = sum of `Missed Incentives`

**Missed incentives — correct methodology for analysis:**
Missed incentives have two components, both computed per row using the same stage-level logic:
- **No opt-in (Part A):** `Adopt Rebate Opt-In Status ≠ "Opted In"` → sum stage amounts where `Stage Completion Date >= Booking Date`
- **Late opt-in (Part B):** `Adopt Rebate Opt-In Status = "Opted In"` → sum stage amounts where `Stage Completion Date < Adopt Rebate Start Date` AND `>= Booking Date`

To avoid double-counting across multiple UCs under the same offer for the same customer, apply the **1 UC per offer** business rule:
1. Compute missed incentives per row (no flag filter needed)
2. Group rows by `(CR Party ID, Track)` — pick the **1 row with the highest missed amount** per group
3. Sum the selected rows to get the total missed per customer or overall

Do **not** filter by `Maximum Incentive Deal Flag` for missed incentives — that flag only applies to Eligible and Expired deals and would exclude rows that contributed to missed amounts.

**Potential remaining** = sum of `Potential Incentives` where `Stage = "Eligible"`

**PVI Engagement score** (per portfolio) = (`PVI Onboard` count ÷ `PVI Eligible` count) × 5 + (`PVI Adopt` count ÷ `PVI Eligible` count) × 5 → score 0–10

**Opt-in opportunities** = rows where `UC 25-50% eligible w/o opt-in = true` or `UC 75% eligible w/o opt-in = true`

**High-risk deals** = rows where `Offer Risk Level = "High"`

**Stage distribution** = count rows grouped by `Current stage`

## Tips for the AI

- Each row is a **deal × use case**. One partner can appear many times (one row per use case).
- To count unique partners: count distinct `CR Party ID` or `BE GEO ID`.
- To count unique deals: count distinct `Deal WS-ID`.
- Dollar amounts (`Booking Amount`, `Estimated Incentive Amount`, `Missed Incentives`, `Estimated Earned Incentives`) are in **USD**.
- `Stage = "Eligible"` means the deal is active and incentive-eligible. `Expired` and `Not Eligible` deals cannot earn new incentives.
- Opt-in operates at the **offer level** (partner × offer), not per use case. If one use case for a partner × offer is opted in, all use cases for that partner × offer are opted in (`Offer opted-in? = true`).
- PVI score excludes the Collaboration portfolio by design.
